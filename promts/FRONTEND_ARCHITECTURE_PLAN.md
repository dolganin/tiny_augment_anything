# План фронтенд-архитектуры для Tiny Augment Anything

## 1. Ограничения и базовые правила

- Общение и вся документация по реализации ведутся на русском языке.
- Реализация только на TypeScript и TSX. JavaScript-файлы не допускаются.
- В коде не использовать комментарии и докстринги.
- При проектировании придерживаться небольших файлов: целевой размер до 250-300 строк, кроме случаев, когда компонент логически невыгодно дробить.
- Каждый этап реализации завершается отдельным git-коммитом.
- Фронтенд должен работать как пошаговый сценарий с жёсткой последовательностью переходов и защитой маршрутов.
- Все модальные окна открываются поверх размытого фона.
- Базовая палитра:
  - `#070a0d` для фона приложения и глубоких тёмных поверхностей
  - `#1d2967` для тёмных карточек, панелей, навигации
  - `#3062bb` для активных рамок, интерактивных элементов, вторичных акцентов
  - `#72b7e0` для hover, подсветок, светлых рамок и фокуса
  - `#f0f0f0` для светлых модалок, треев, текста на тёмном фоне
  - `#e06971` для ошибок и критических состояний
- Основной шрифт: JetBrains Mono или JetBrains Sans, если в макетах нужен менее технический тон. Внутри проекта лучше сразу зафиксировать один вариант, чтобы не разъезжалась типографика.

## 2. Цель фронтенда

Фронтенд должен провести пользователя через полный pipeline:

1. Загрузка zip-архива датасета.
2. Валидация и обработка датасета на бэкенде.
3. Просмотр статистики классов и выбор классов для аугментации.
4. Выбор режима обучения диффузионной модели.
5. Просмотр логов дообучения.
6. Выбор одного из двух режимов:
   - генерация новых изображений по текстовому промпту
   - модификация существующих изображений выбранных классов
7. Подтверждение или отклонение сгенерированных результатов.
8. Запуск обучения классификатора на итоговом датасете.
9. Просмотр метрик Precision и Recall.
10. Скачивание готового датасета.

## 3. Рекомендуемый стек

- `React 19`
- `TypeScript`
- `Vite`
- `React Router`
- `TanStack Query`
- `Zustand`
- `React Hook Form`
- `Zod`
- `Recharts`
- `Axios`
- `clsx`

### Обоснование выбора

- `React Router` нужен для явного сценарного роутинга между этапами.
- `TanStack Query` подходит для запросов, мутаций, опроса долгих задач и кэширования статуса.
- `Zustand` нужен для компактного глобального store с данными сессии: `datasetId`, выбранные классы, режим, id задач, результаты.
- `React Hook Form` и `Zod` дадут контролируемую форму для генерации и редактирования YAML-параметров.
- `Recharts` проще и легче, чем Plotly, для кастомных столбчатых диаграмм без осей и с ручной расстановкой подписей.
- `Axios` остаётся самым удобным вариантом для Python API, загрузки файлов и отмены запросов.

## 4. Архитектурный принцип

Нужна архитектура не вокруг отдельных страниц, а вокруг одного длинного пользовательского сценария. Внутренне это лучше оформить как workflow со стадиями, а маршруты использовать как представление стадий.

Ключевая идея:

- Роут отвечает за конкретный экран.
- Глобальный store отвечает за текущую стадию и артефакты сессии.
- Query-слой отвечает за общение с API и опрос задач.
- Route guard не даёт попасть на поздний этап без завершения предыдущего.

## 6. Маршруты

- `/` и `/upload`
  - экран загрузки zip-архива
- `/dataset/stats`
  - диаграмма распределения классов и выбор классов
- `/diffusion/fine-tune`
  - выбор дообучения и окно логов
- `/mode`
  - модалка выбора: `Генерировать` или `Модифицировать`
- `/generate`
  - текстовый промпт, редактирование параметров, запуск генерации
- `/modify`
  - выбор изображения из выбранных классов, параметры модификации, запуск
- `/review`
  - просмотр результатов и подтверждение или отклонение
- `/classifier/train`
  - ожидание дообучения классификатора и вывод логов прогресса
- `/metrics`
  - визуализация Precision и Recall
- `/download`
  - итоговый экран со скачиванием архива

## 7. Route guard правила

- На `/dataset/stats` можно попасть только при наличии успешной загрузки и `datasetId`.
- На `/diffusion/fine-tune` можно попасть только после выбора хотя бы одного класса.
- На `/mode`, `/generate`, `/modify`, `/review` можно попасть только после завершения этапа выбора классов и фиксации режима.
- На `/classifier/train` можно попасть только после подтверждения хотя бы одного результата генерации или модификации.
- На `/metrics` можно попасть только после успешного завершения обучения классификатора.
- На `/download` можно попасть только после получения метрик и готовности архива.

## 9. Сценарная декомпозиция по экранам

### 9.1 Экран загрузки датасета

- Центральная зона с крупной SVG-иконкой загрузки.
- Клик по SVG открывает скрытый `input[type=file]` с фильтром `.zip`.
- После выбора архива запускается `POST` загрузка файла.
- Пока идёт валидация, показывается анимированный loader.
- При ошибке открывается светлая модалка с красной рамкой `#e06971`.
- При успехе сохраняется `datasetId` и выполняется переход на `/dataset/stats`.

### 9.2 Экран статистики датасета

- Бэкенд отдаёт JSON с количеством изображений по классам.
- Фронтенд сортирует данные по убыванию только если это не гарантирует бэкенд.
- На экране показываются только 10 классов.
- Нужна вертикальная диаграмма без осей.
- Название класса выводится справа от соответствующего столбца или в правом списке, жёстко привязанном к столбцам.
- Класс выбирается кликом по скруглённому голубому тегу.
- Выбранное состояние фиксируется визуально.
- Кнопка вперёд активна только если выбран хотя бы один класс.
- Кнопка назад возвращает на экран загрузки.

### 9.3 Экран решения о дообучении

- Пользователь выбирает: дообучать диффузионную модель или пропустить этап.
- Если выбран fine-tune, отправляется запрос на запуск.
- Прогресс приходит через polling, SSE или WebSocket.
- Отображаются эпоха, loss, ориентировочное оставшееся время, статус задачи.
- После успеха открывается следующий экран `/mode`.

### 9.4 Экран выбора режима

- Модальное окно с двумя крупными действиями:
  - `Генерировать`
  - `Модифицировать`
- Под каждой кнопкой короткое пояснение сценария.
- После выбора режим сохраняется в store.

### 9.5 Экран генерации по текстовому промпту

- Левая часть: поле промпта.
- Правая часть: список параметров, пришедших с бэкенда на основе YAML-конфига, уже преобразованного в JSON.
- Все поля редактируются как текстовые с последующим типизированным преобразованием перед отправкой.
- Отдельное поле для количества сэмплов.
- После запуска показывается loader с ощущением диффузионного процесса.
- При завершении показывается экран `/review`.

### 9.6 Экран модификации изображения

- Бэкенд возвращает случайное изображение из выбранных классов.
- Пользователь видит исходное изображение и поля конфигурации.
- Есть поле количества модификаций.
- Запуск задачи аналогичен генерации.
- После завершения переход на `/review`.

### 9.7 Экран review

- Пользователь получает результирующие изображения партиями.
- Для каждого изображения доступны действия:
  - принять
  - отклонить
- При отклонении фронтенд сразу вызывает endpoint удаления временного результата.
- Важно поддержать сценарий пакетной проверки, если результатов несколько.
- После набора подтверждённых результатов пользователь может запустить обучение классификатора.

### 9.8 Экран обучения классификатора

- После подтверждения пользователем вызывается backend hook запуска классификатора.
- Показывается анимированный экран ожидания.
- Логи и прогресс выводятся аналогично fine-tune.
- После успеха переход на `/metrics`.

### 9.9 Экран метрик

- Две отдельные панели или две модалки на одном экране.
- Слева Recall.
- Справа Precision.
- Precision отображать красной серией, Recall зелёной серией.
- Диаграммы строить столбцами по классам.
- Нужны аккуратные подписи и ограничение по количеству классов на одном экране, если их очень много.

### 9.10 Экран скачивания

- Пользователь получает кнопку скачивания итогового архива.
- По нажатию выполняется скачивание уже готового файла.
- Нельзя строить UX вокруг очень долгой генерации архива после клика.
- Бэкенд должен выдавать уже подготовленный ресурс или ссылку на него.

## 10. UI-система

### Поверхности

- Основной фон приложения: тёмный `#070a0d`.
- Главные панели: `#1d2967`.
- Светлые модалки и треи: `#f0f0f0`.
- Обводки интерактивных светлых блоков: `#72b7e0`.

### Кнопки

- Основные кнопки: тёмные заливки.
- Текст на кнопках всегда белый.
- Hover строить через усиление свечения и лёгкий сдвиг яркости.
- Disabled-состояние делать очевидным визуально и по курсору.

### Выбранные теги классов

- Базовое состояние: светлая поверхность с голубой рамкой.
- Hover: усиление рамки и фона.
- Active: плотная голубая заливка и контрастный текст.

### Модалки

- Фон позади обязательно размывать.
- Ошибки выделять красной рамкой `#e06971`.
- Закрытие по кнопке-крестику должно быть явно заметным.

### Анимации

- Loader загрузки датасета: вращающийся круг или орбитальный индикатор.
- Loader обучения: более сложная анимация, напоминающая распад шума в сигнал.
- Анимации должны быть достаточно выразительными, но не мешать чтению логов.

## 12. Нормализация типов данных на фронтенде

- Выделить отдельный слой адаптеров между API и UI.
- Никогда не тащить сырой backend JSON напрямую в компоненты.
- Для YAML-конфигов нужен явный словарь типов:
  - `string`
  - `number`
  - `boolean`
  - `enum`
- Перед отправкой изменённого конфига фронтенд должен выполнять преобразование типов и валидацию.

## 13. Ключевые риски

- Неопределённый формат долгих задач: polling, SSE и WebSocket дают разный фронтенд-контур.
- Неясно, как backend отдаёт изображения: `base64`, URL, blob или временный файл.
- Неясно, как восстанавливается пользовательская сессия после перезагрузки страницы.
- Не определены лимиты на размер zip-архива и длительность обработки.
- Не определён способ отображения очень большого числа классов в метриках.
- Не определён минимальный сценарий, если пользователь не хочет fine-tune.

## 14. Вопросы, которые нужно закрыть до начала реализации

1. ОТВЕТ: должен использоваться WebSocket и соединение на нём.
2. ОТВЕТ: после перезагрузки должно восстанавливатьсят текущее состояние обработки.
3. ОТВЕТ: идентификатор рабочей сессии.
4. ОТВЕТ: бэкенд сам будет сортировать классы по айтемам.
5. ОТВЕТ: самые редкие классы (те, у которых меньше всего изображений)
6. ОТВЕТ: бэкенд будет отдавать путь внутри контейнеров до картинок.
7. ОТВЕТ: подтвереждение или отказ происходит по одной штуке.
8. ОТВЕТ: нет, будет проводиться ровно столько генераций, чтобы нарастить то количество элементов, которые запросил пользователь.
9. ОТВЕТ: бэкенд сразу его удаляет.
10. ОТВЕТ: бэкенд будет присылать только те поля, которые могут быть редактируемы
11. ОТВЕТ: если пользователь пропускает fine-tune, то по умолчанию доступна только модификация.
12. ОТВЕТ: авторизация не нужна, это будет локальное приложение для одного человека.
13. ОТВЕТ: так как это локальное хранилище, то ссылка должна работать постоянно, пока работает контейнер, и хранить его нужно просто как .zip.
14. ОТВЕТ: пока что истрия с предыдущих запусков не нужна.
15. ОТВЕТ: никакая, нужно просто повторять генерации до тех пор, пока не наберется целевое количество данных, если пользователь сам не решит прервать этот процесс.

## 16. Требования к качеству реализации

- Все новые модули писать сразу типизированными.
- Компоненты не смешивают бизнес-логику, сетевые запросы и визуализацию в одном файле.
- Для каждой фичи нужен свой локальный набор типов, хуков, UI-компонентов и API-операций.
- Большие сценарии разбивать на контейнеры и презентационные блоки.
- Ошибки API нормализовать в единый формат для модалок и уведомлений.
- Все долгие операции должны поддерживать понятный статус:
  - `idle`
  - `pending`
  - `success`
  - `error`
  - `cancelled`, если backend это поддержит

## 17. Итоговое решение по архитектуре

Для этого проекта лучше всего подойдёт модульный React SPA на TypeScript с явным workflow-роутингом, глобальным store текущей сессии, типизированным API-слоем и отдельными feature-модулями под каждый этап pipeline. Это даст контролируемый сценарий, нормальную интеграцию с Python-бэкендом и позволит реализовать сложную цепочку без превращения интерфейса в один большой компонент.
